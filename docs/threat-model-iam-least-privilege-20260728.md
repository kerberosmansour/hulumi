# Threat Model — IAM Least Privilege — password policy, role scoping, access analyzer, MFA

> Generated by the [`/hulumi-threat-model`](https://github.com/kerberosmansour/hulumi) Claude Code skill. After source-accuracy review, this consumer-specific document retains only applicable NIST SP 800-53 Rev 5 identifiers. See [`docs/mappings/licensing.md`](https://github.com/kerberosmansour/hulumi/blob/main/docs/mappings/licensing.md) for the IDs-only policy.

## Scenario

An engineer is standing up IAM baselines for a new AWS account: password
policy, Access Analyzer, role scoping for IaC and application workloads, MFA
enforcement, and the `hulumi:iac-role=true` tag convention that the drift
classifier depends on. The public `AccountFoundation` component internally
supplies the account password policy and, for Startup-Hardened, an account-local
Access Analyzer; its public IAM-baseline output is `iamBaselinePolicyArns`.
Workload-role scoping, MFA enforcement, analyzer archive rules and broader
wildcard-resource prevention remain separate controls and are not claimed as
outputs of that component.

## Actors

- Platform Engineer (trusted)
- AI Coding Agent (trusted, authoring IaC)
- External Attacker (via stolen IAM access key)
- Compromised CI runner (semi-trusted, could exfil if over-scoped)

## Assets

- IAM user passwords and access keys
- IAM roles and their assume-role trust policies
- IAM policies attached to roles
- `hulumi:iac-role=true` tag — load-bearing for genuine IaC-deployment-role
  attribution and forbidden on workload identities

- `hulumi.baseline.aws.AccountFoundation` — Shipped in M3 (v0.3). The public
  component creates an account password policy and, for Startup-Hardened, one
  account-local Access Analyzer; its public IAM-baseline output is
  `iamBaselinePolicyArns`. It does not expose an `iamBaseline` component or
  property and does not create workload-role policies, MFA, analyzer archive
  rules or generic inline-policy prevention.
- `hulumi.policies.aws.HulumiHardeningPack (H3 rule: iac-role tag present)` —
  Shipped in M2 advisory; mandatory at v1.0 (M5) + SCP-paired. H3 detects a
  missing `hulumi:iac-role=true` tag at preview time. The current rule applies
  to every IAM role, and `SecureWorkloadRole` currently adds the tag
  automatically; that behavior is incompatible with #255 until H3 and the
  shared constructor distinguish genuine deployment roles from workload roles.
  The SCP template `docs/deployment/scp.json` protects the tag server-side. H3
  is not a generic IAM wildcard-policy rule.
- `hulumi.policies.aws.CisV5Pack (current IAM subset)` — Shipped in M3
  (v0.3). The current subset checks password minimum length, password reuse,
  the exact full-administrator policy pairing for the array-shaped IAM
  `Statement` input covered by its tests, and advisory Access Analyzer presence.
  It does not currently reject the equally valid single-object `Statement`
  representation or enforce MFA or IAM credential rotation.

## Consumer Overlay — Secure Aurora Application Principal (#255)

Issue [#255](https://github.com/kerberosmansour/hulumi/issues/255) applies this
scenario to a stateful workload that currently uses one Kubernetes
ServiceAccount and one IRSA role for both schema migration and request-serving
database access. The application can therefore re-read the Aurora master
secret after startup. Changing PostgreSQL roles inside that same process does
not create a durable authority boundary.

No shipped Hulumi primitive currently composes the migrator/runtime identity
split, application-principal bootstrap and rotation lifecycle. `SecureSecret`
remains the intended value-free secret-container primitive; #255 owns the
missing cross-boundary composition. Issue #40's `RdsCredentialSecret` is
unconditionally incompatible with this composition: it reads the master value
during Pulumi evaluation and renders that value into a Kubernetes Secret, so
the value transits Pulumi state and etcd even if serving-workload RBAC cannot
read the resulting Secret.

### Required Architecture and Acceptance Gates

1. **Non-interchangeable Kubernetes workload identities.** The component
   renders distinct runtime and migrator ServiceAccounts, exact IRSA trust
   policies and pod/Job templates. Any Kubernetes-hosted rotation or
   current-credential retrieval broker receives another exact, non-interchangeable
   ServiceAccount and workload envelope. The serving workload names only the
   runtime ServiceAccount; the migration Job names only the migrator
   ServiceAccount. Tests reject a runtime pod that mounts any privileged
   projected token, the master credential or a master-derived Kubernetes
   Secret. Runtime and deployment-controller identities are forbidden from
   creating `serviceaccounts/token` for, or impersonating, every migrator,
   rotation and broker identity. Pairwise live negatives run from runtime,
   deployment, migrator, every rotation and retrieval-broker identity, and every
   unlisted identity to every privileged ServiceAccount, including the caller's
   own ServiceAccount. No workload identity may create/update/patch a
   `kubernetes.io/service-account-token` Secret for one of those accounts,
   get/list/watch such a Secret, or consume it through a Secret volume, a
   projected-volume `secret` source, `env.valueFrom.secretKeyRef` or
   `envFrom.secretRef`. Admission rejects the token-Secret type and
   `kubernetes.io/service-account.name` annotation for every workload request
   identity. Any unavoidable control-plane or break-glass exception is named
   exactly, unavailable to workloads and tested separately; an implicit
   privileged-workload exception is forbidden. RBAC and admission fixtures also reject
   create/update/patch of Pod, Deployment, ReplicaSet, StatefulSet, DaemonSet,
   Job and CronJob templates that name any privileged ServiceAccount. Runtime
   and deployment identities are denied `pods/exec`, `pods/attach`,
   `pods/portforward`, `pods/ephemeralcontainers`, `pods/proxy`,
   `services/proxy` and every discovered `nodes/*` path that could enter,
   observe or control any privileged workload. Release-time Kubernetes API
   discovery inventories every `pods/*`, `services/*` and `nodes/*`
   subresource; an unclassified addition fails closed. Actual-identity RBAC
   negatives reach every discovered entry, explicitly including kubelet log,
   pod-inventory, stats, metrics, health, configuration and checkpoint paths.
   Direct kubelet reachability is probed separately from API-server proxy
   reachability and must be absent from workload networks. A proxy or kubelet
   path is permitted only as an exact named positive matrix row with its
   application-layer authentication, caller/target envelope, operation and
   enforcing policy attributed; a broad proxy grant cannot satisfy the gate.
   Role/ClusterRole `bind` and `escalate` plus
   RoleBinding/ClusterRoleBinding mutation are tested as their own privilege
   paths rather than described as ServiceAccount operations.
   Pairwise live negatives also reach-test denial of `impersonate` for users,
   groups, ServiceAccounts, UIDs and user extras from every actual runtime,
   deployment, migrator, rotation and broker identity. The same matrix denies
   certificate-signing-request creation, approval and signer use; `aws-auth`
   mutation; and EKS authentication-mode, access-entry and
   access-policy-association mutation. Release evidence inventories every
   resulting Kubernetes user and group and proves that none gives a workload or
   deployment identity a privileged effective identity. Any required
   certificate approver, signer or EKS access administrator is named exactly,
   is not a workload identity and is separately bounded with positive and
   negative controls.

   The admission allowlist contains the exact serving Deployment/Pod envelope
   plus one exact envelope for every selected Kubernetes-hosted privileged
   workload: the migration Job, each rotation Job/controller and any
   retrieval-broker Deployment/Pod. Runtime, deployment-controller and workload
   identities may create only their own named envelopes. Each envelope is bound
   to its named controller, namespace, ServiceAccount, immutable image digest,
   command, arguments, projected-token shape and workload digest. It pins every
   application, init, sidecar and ephemeral container; security context,
   privilege-escalation setting and capability set; host namespace; volume,
   `hostPath` and device; runtime class; node placement and toleration. Restricted
   Pod Security or a stricter posture is enforced, and every necessary exception
   is exact and separately reviewed. Migration, rotation and credential-broker
   workloads use node pools disjoint from the lower-trust serving runtime, or an
   explicitly approved sandboxed or virtualized runtime with equivalent
   compute-isolation evidence. Privileged-pool labels use the Node authorizer
   and `NodeRestriction` protected-label prefix; required node affinity plus
   exact taints and tolerations select the pool, and the serving envelope is
   denied from every privileged node. Arbitrary Pods, PersistentVolumes,
   container-runtime sockets and other node-access paths are denied. Near-match
   tests for every envelope change each field, add a container, alter projected
   tokens or node-access settings and vary names, labels or ownership; every
   mutation is rejected. Live tests also prove the actual workloads schedule on
   the intended disjoint nodes, workload identities cannot mutate protected
   labels or taints, and every placement near-match fails. Production defaults
   to a native
   `ValidatingAdmissionPolicy`; an explicitly selected Kyverno or Gatekeeper
   adapter may enforce the same assertions. Runtime, deployment and other
   workload identities cannot mutate or delete the policy, its binding,
   parameter resources, namespace labels/selectors, webhook configuration or
   enforcing controller. Unsupported, absent or unbound admission enforcement
   fails closed.

   Live-cluster tests use the actual identities. They prove every negative while
   each named controller can create its exact positive workload. After migration
   validation, the real serving controller creates the exact Deployment and
   ReplicaSet, its Pod is admitted and becomes Ready under the production
   ServiceAccount, admission binding, runtime class and node placement.
   Controller-created Pods also start for migration, rotation and retrieval
   separately whenever that workload is selected. Every positive and negative
   decision records the enforcing policy and binding, so a deny-all or unbound
   admission path cannot satisfy the gate. Node-role and every EKS credential
   path are inventoried. Runtime and privileged workloads cannot obtain node
   credentials through IMDS; `hostNetwork` is prohibited or isolated by an
   independently tested boundary, and node IMDS hop/metadata controls are
   release evidence.

2. **Effective AWS denial, not policy-text absence.** Evaluation includes every
   inline, attached, session, permissions-boundary, Organizations SCP/RCP,
   VPC-endpoint, secret-resource and KMS-key policy, plus every live KMS grant,
   the production request context and every permitted egress route. A reviewed
   action/resource/request-context matrix covers the runtime, migrator, rotation
   and any current-credential retrieval-broker identities separately. Each
   matrix cell names the exact permitted secret ARN and stage, KMS key and
   encryption context, role, source endpoint, session attributes and operation;
   every unlisted cell is denied. Runtime is denied master-secret value/version
   operations and master-key `kms:Decrypt`, and cannot assume migrator or
   rotation roles. The migrator, rotation and retrieval broker receive only
   their enumerated cells rather than a shared privileged exception. Pulumi
   mocks and IAM simulation inspect the rendered design but are never release
   evidence by themselves. Before release, live calls from each actual identity
   traverse the intended VPC endpoint and every alternate allowed egress path.
   Positive controls exercise each required matrix cell. Negative calls cover
   unrelated secrets, unauthorized stages and version IDs, unrelated KMS keys
   and encryption contexts, `sts:AssumeRole`, `iam:PassRole`, IAM/policy
   mutation, rotation reconfiguration and KMS grant creation/change/retirement.
   Pairwise live negatives also invoke `sts:AssumeRoleWithWebIdentity` using
   each actual projected token and audience against every other workload role,
   with an intended-token positive control. Any IRSA correction or retirement
   inventories and closes every former OIDC provider, issuer, `sub`, `aud`,
   role-trust condition and ServiceAccount annotation path. Rollout then blocks
   on two independent retirement gates. First, every pre-cutover STS credential
   is denied by a fully propagated durable authorization cutoff keyed on
   `aws:TokenIssueTime`, or by waiting through the maximum STS-session lifetime.
   A cutoff is selected only after trust-policy propagation and after every
   old-token assumption path is closed or the old token has expired; its
   timestamp is therefore later than the last possible session issuance from
   that token, including issuance during propagation. Second, the projected JWT
   itself is denied by every former role and the intended new binding, either
   because the new trust requires an issuer, `sub` and `aud` claim set that the
   old token cannot satisfy, or after complete Pod drain plus the maximum token
   acceptance lifetime, including IAM's five-minute OIDC clock-skew allowance.
   Live tests retain both a projected token minted before cutover and AWS
   credentials already issued from it. The retained token is denied when it
   invokes `sts:AssumeRoleWithWebIdentity` against every former role and the
   intended new role, while a newly minted token succeeds against the intended
   new role. Independently, the retained credentials are denied against every
   formerly authorized resource and action while an independently verified
   resource positive control succeeds. Both old artifacts must be unusable
   before rollout continues.
   When EKS Pod Identity is installed or available, release evidence enforces
   an exact association allowlist over cluster, namespace, ServiceAccount, role
   ARN, optional target-role ARN, external ID, session policy and session-tag
   posture; every unlisted association or field mismatch fails. From actual
   intended and unlisted Pods, live tests query the Pod Identity agent directly,
   independently of IRSA and default credential-chain selection, and verify the
   returned principal, target role, session attributes and effective
   authorization with positive and pairwise-negative controls. Workload and
   deployment identities are denied association create/update/delete, add-on
   credential-binding mutation, `iam:PassRole`, target-role chaining and
   `eks-auth:AssumeRoleForPodIdentity`. Association correction or retirement is
   bracketed by a durable authorization denial or complete Pod and agent drain,
   followed by the maximum Pod Identity cache and STS-session lifetime; every
   credential issued before the change must be unusable before rollout
   continues. Equivalent future credential-binding APIs enter the matrix
   fail-closed.
   Every existing grant on every involved KMS key is inventoried by grant ID,
   grantee, retiring principal, operations, source ARN and encryption-context
   constraints; an unlisted grant fails the matrix. Tests wait for grant
   propagation before accepting the resulting effective cryptographic denial.

   Every negative cell is non-vacuous. An independently authorized observer
   proves the target secret, exact version/stage, KMS key and valid ciphertext,
   role, endpoint and route exist. The exact request succeeds for its authorized
   control identity, then the tested identity receives the expected
   authorization denial from a named durable layer; `ResourceNotFound`,
   `InvalidCiphertext`, DNS, network and route failures are not authorization
   evidence. KMS authorization-only dry runs are used where supported. Runtime
   master operations remain denied while the bounded current-credential path
   succeeds. Evidence identifies at least one durable non-network denying
   layer, and a test-stack mutation that makes the endpoint policy permissive
   must remain denied. Value-free CloudTrail and endpoint/flow receipts tie the
   calls to the expected principal, route and resources; absence of CloudTrail
   alone is not accepted as a denial.

   Only the genuine IaC deployment role carries `hulumi:iac-role=true`.
   Runtime, migrator, rotation and retrieval-broker roles must not carry or add
   it. H3 is scoped to deployment roles, or a narrow reviewed discriminator
   suppresses only the closed workload-role set; the shared workload-role
   constructor no longer adds the tag. A live workload-role CloudTrail event is
   not filtered, while a genuine IaC-role event is.

3. **Secrets do not transit Pulumi or etcd.** `SecureSecret` creates the
   value-free application-secret container. No component in this composition
   performs `GetSecretValue` during Pulumi evaluation, and
   `RdsCredentialSecret` is rejected from this composition. In the tenant-bound
   identity design, the serving identity receives only its current application
   credential through a path that cannot request arbitrary version IDs or
   non-current stages. In the database-authorization-broker design, the
   application runtime receives no database credential; only the separately
   trusted broker receives the current application credential. If Secrets
   Manager authorization cannot enforce the current-only boundary directly, the
   serving/runtime IRSA has no `GetSecretValue` permission and a separately
   trusted current-only broker performs retrieval. The bounded
   migration/rotation identities read the application secret plus the master
   secret they require. Manifests, outputs, state, test fixtures, errors and
   logs remain value-free.
4. **Evidence-backed alternating-user rotation.** The supported production
   posture uses two bounded direct-login PostgreSQL principals for each serving
   authorization scope, with identical explicit grants. Those principals belong
   to the tenant-bound workload or the separately trusted database broker, never
   to an application runtime that the broker design excludes from the database.
   A rotation identity owns password generation,
   Secrets Manager version staging, database password change, `AWSPENDING`
   login/authorization testing, `AWSCURRENT` promotion and stale-stage
   retirement. The production Aurora cluster parameter group pins
   `rds.restrict_password_commands=1`; release evidence observes the parameter
   in its applied/in-sync state and proves that any required reboot completed.
   No bounded login is a direct or indirect member of `rds_password`.
   Actual-login negatives prove `ALTER ROLE CURRENT_USER PASSWORD ...`,
   `PASSWORD NULL` and `VALID UNTIL ...` are denied, while the exact rotation
   identity has a positive control for only the password operations it needs.
   Replica connection age and rollout deadlines bound credential overlap. At
   every point before `NOLOGIN` and throughout the topology bracket, rotation
   proves that no login-capable role has a direct or indirect `SET` or `INHERIT`
   path into the retiring alternating principal and that no live superuser or
   `SET SESSION AUTHORIZATION`-capable session can assume it. Rotation revokes
   any such path and terminates every affected session before drain evidence may
   begin. It re-inventories memberships and capable sessions after
   prepared-transaction cleanup; a membership change, surviving effective-role
   path or reappearing retiring-role prepared transaction invalidates the
   bracket and aborts retirement. At the drain deadline, rotation sets the
   retiring role `NOLOGIN` and discovers
   every current Aurora DB instance on which the superseded login could have
   authenticated, including the writer, every reader and every applicable
   custom-endpoint member. Through each instance endpoint, it observes
   `rolcanlogin = false` and proves password authentication, plus IAM or Kerberos
   authentication when enabled, is denied while an independently authorized
   reachability control succeeds. An unavailable or recovering instance,
   mismatched inventory, or failure that cannot be attributed specifically to
   authentication aborts retirement. The authentication-denial and subsequent
   drain checks are bracketed by matching complete
   cluster/instance/endpoint-membership inventories.

   Each topology bracket also inventories every RDS Proxy, proxy endpoint,
   target group and other authentication or pooling intermediary, including
   cross-VPC endpoints. Release either proves that no intermediary exists or
   blocks new authentication and proves that both client-side and database-side
   sessions for the retiring identity are closed and cannot be transparently
   re-established. Role reuse is forbidden until the maximum surviving
   intermediary session and token lifetime has elapsed. An unobservable or
   unsupported intermediary, or a changed intermediary inventory, invalidates
   the bracket and aborts retirement.

   Rotation connects through each instance endpoint rather than relying on a
   load-balanced cluster or reader endpoint, enumerates by role OID every
   matching `pg_stat_activity` backend on that server, terminates each with
   `pg_terminate_backend(..., <positive-bounded-timeout>)`, and proves a
   pre-existing canary session on every applicable instance is disconnected and
   no matching backend remains there. A failover, instance recovery, replica
   addition/removal or custom-endpoint membership change invalidates the
   bracket: rotation repeats complete topology discovery, per-instance
   `rolcanlogin` observation, non-vacuous authentication denial and zero-backend
   proof against the new inventory before continuing.

   Backend-zero is not by itself retirement evidence. Release evidence either
   observes `max_prepared_transactions = 0` in its applied, reboot-complete state
   on every current instance and proves `PREPARE TRANSACTION` is rejected, or,
   after new logins are blocked and every retiring-role backend is gone,
   enumerates every permitted database, rolls back every `pg_prepared_xacts`
   entry owned by the retiring role in the database that owns it, and proves no
   matching prepared transaction remains anywhere. The nonzero configuration
   path uses a retiring-role prepared-transaction canary to prove that a zero
   `pg_stat_activity` count does not pass the gate and that cleanup fails closed.
   Only then may rotation replace the password and retire the mapping or secret
   stage; live authentication with the prior credential also fails. The next
   cycle may
   reactivate that alternating principal only through a newly tested
   `AWSPENDING` value. In the tenant-bound identity
   design, a protected one-to-one `session_user` mapping for the reactivated
   login is created and validated before its `AWSPENDING` authorization probe
   and stage promotion; the superseded mapping is retired only after connection
   drain and credential retirement prove it unreachable. Runtime negative tests
   prove that prior/non-current stages and version IDs cannot be retrieved. The
   component creates or references the real rotation resource and emits
   strategy-specific states such as `unconfigured`, `configured_unverified`
   and `alternating_users_verified`. It must not reuse `SecureSecret`'s current
   Boolean-derived `"enabled"` output as evidence.

5. **Explicit PostgreSQL 16 non-administrative authority allowlist.** The complete
   bounded-login allowlist applies to every non-administrative database-capable
   identity: both alternating users, every broker login, every aggregation
   login, all roles reachable through `SET ROLE` or direct/indirect membership,
   and `PUBLIC`. Privileged bootstrap, migration and rotation sessions are
   governed separately by gate 6 rather than forced into this bounded-login
   shape. Any intentional difference is an explicit matrix row with a positive
   control and negative boundary tests; “non-serving” is not an exemption. Every
   bounded login is `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`,
   `NOREPLICATION` and `NOBYPASSRLS`. In every permitted database, a
   source-version-pinned enumeration of every owner-bearing PostgreSQL 16
   catalog proves that no bounded or reachable role owns or can alter any
   unlisted object. The enumeration includes databases, schemas, relations,
   sequences, views, materialized views, routines, types, extensions, large
   objects, foreign-data wrappers, foreign servers, procedural languages,
   tablespaces, text-search configurations and dictionaries, collations,
   conversions, operators, operator classes and families, publications,
   subscriptions, extended statistics and event triggers. Reached owner-only
   `ALTER` and `DROP` negatives cover every populated class, with privileged
   positive controls; the complete implicit-execution closure is rerun after
   every authorized DDL change. No reachable bounded path has privileged `SET`,
   `ALTER SYSTEM`, `ADMIN` or inherited authority, database/schema `CREATE`,
   database `TEMP`, migration-ledger mutation or blanket/default function
   execution. Every `pg_database` row and effective `CONNECT` path, including
   grants through `PUBLIC`, is enumerated.
   Only explicitly reviewed application databases are connectable; actual-login
   probes fail to connect to `postgres`, `template1` and every other database,
   and the complete authority scan runs independently inside every permitted
   database.

   The table privilege allowlist names only the required subset of `SELECT`,
   `INSERT`, `UPDATE` and `DELETE`; sequence `USAGE` or `SELECT` is granted only
   to named sequences whose reviewed write path requires it. Only reviewed
   directly executable routines and reviewed implicit code hooks reachable from
   an allowed data, conversion, constraint, index or maintenance path may
   execute; a missing ordinary routine `EXECUTE` grant is not denial evidence
   for an implicit hook. For every actual creator role, object type and
   applicable schema combination, inspection computes and allowlists the
   effective future-object ACL: it synthesizes PostgreSQL's hard-wired default
   when no global `pg_default_acl` row exists and unions every applicable
   per-schema addition rather than treating an absent row as empty. The scan
   covers relations, sequences, routines, types and schemas under the actual
   `current_user`; inherited-role defaults are not substituted. In-transaction
   canary creation under each actual creator proves the exact expected owner
   ACL, `PUBLIC` ACL and grant-option closure before rollback. Migration
   transactions establish final ownership, grants, default ACLs and RLS policy
   before commit so runtime cannot observe a permissive intermediate object.
   Effective column privileges and grant options are inspected for every
   column, including independently granted `SELECT`, `INSERT`, `UPDATE` and
   `REFERENCES`; relation ACLs alone are not accepted as proof. Effective grant
   options on databases, schemas, relations, sequences, routines, types and
   columns are absent unless a named matrix row separately justifies the
   delegation with a live positive control and negative boundary tests. On
   PostgreSQL 16, effective ACL inspection proves `TRUNCATE`, `REFERENCES` and
   `TRIGGER` absent for every relation and role path. Ownership and database
   ownership are checked separately because PostgreSQL 16 has no table-level
   `MAINTAIN` privilege. Tests first assert effective ACL, default-ACL and
   column-ACL results, then use fixtures that satisfy all prerequisite schema,
   relation, routine and object conditions, reach the named permission check
   and return the expected SQLSTATE; a privileged positive control proves each
   fixture is non-vacuous.

   The complete PostgreSQL 16 authority scan also covers every large object,
   foreign-data wrapper, foreign server and user mapping, procedural language,
   tablespace and configuration-parameter ACL. It evaluates ownership,
   `PUBLIC`, direct/indirect reachable roles, effective privileges and grant
   options; every unlisted instance is absent. Reached actual-login probes prove
   large-object read/write, foreign-table reads/writes and remote side effects,
   privileged parameter `SET`/`ALTER SYSTEM`, language use and tablespace
   creation are denied, with authorized positive controls where an instance is
   intentionally allowlisted. These negatives satisfy every unrelated
   prerequisite before reaching the named authorization check. They include
   `CREATE SERVER` against an existing wrapper to exercise foreign-data-wrapper
   `USAGE`; `CREATE FOREIGN TABLE` against an existing server to exercise server
   `USAGE`; and `CREATE`, `ALTER` and `DROP USER MAPPING FOR CURRENT_USER` against
   existing fixtures. Tablespace evidence uses `CREATE TABLE ... TABLESPACE` and
   `CREATE INDEX ... TABLESPACE` against an existing tablespace to exercise its
   `CREATE` ACL; `CREATE TABLESPACE`, whose superuser check would be vacuous for
   that purpose, is not accepted as the ACL probe. Each operation records the
   expected reached SQLSTATE/check and has an authorized positive control.

   Actual-login `REINDEX TABLE`, `CLUSTER`, `ALTER TABLE` and every
   component-used maintenance operation are likewise denied by non-ownership
   and proven with reached commands and privileged controls. Every
   `SECURITY DEFINER` routine has a fixed, safe `search_path` and a non-runtime
   owner.

6. **Privileged PostgreSQL sessions are separately bounded.** A reviewed matrix
   covers the actual `session_user` and `current_user` for bootstrap, migration
   and rotation; every direct/indirect membership, role attribute, owned object,
   permitted DDL/role/password operation, connection source, database, session
   setting and secret stage; and the maximum session and credential lifetime.
   Each permitted operation has a reached positive control. Every unlisted
   operation is denied with actual-login tests, including unrelated role or
   password changes, ownership transfer, extension/language installation,
   arbitrary routine execution, security-label/event-trigger changes,
   database/schema creation, replication and cross-database access.

   Master authority is confined to an explicitly enumerated, time-bounded
   initial-bootstrap or break-glass recovery path and is never a steady-state
   serving credential. Steady-state migration and rotation use dedicated
   least-privilege database principals wherever master authority is unnecessary.
   If a reached PostgreSQL/Aurora limitation proves a master-authorized operation
   unavoidable, the matrix names that exact operation, time/session bound and
   connection source, rejects every sibling operation, and records approved
   residual risk. Post-session tests prove the privileged credential is absent
   from serving workloads and cannot be reused outside the authorized envelope.

7. **All query surfaces preserve the tenant boundary.** Catalog inspection
   enumerates every effectively accessible view, materialized view and rewrite
   rule plus its complete `pg_depend` base-object graph for both alternating
   users, broker, aggregation, reachable roles and `PUBLIC`. A view is denied or
   is a reviewed PostgreSQL 16 `security_invoker=true` view whose full dependency
   graph preserves the caller's tenant isolation. Every reachable non-view
   rewrite rule is separately enumerated with its event, owner, security context
   and complete read/write dependency graph; it is denied or explicitly
   approved only after actual-login side-effect tests prove the tenant boundary.
   Materialized data is separately isolated with tenant-qualified storage and
   refresh authority; it is never treated as RLS-preserving merely because its
   source tables use RLS. Victim-tenant probes execute through every allowed
   view, materialized-view read path, rewrite rule and routine surface.
8. **Runtime RLS behavior is proved end to end.** Every tenant table has RLS
   enabled and forced, with catalog inspection of exact policy roles, commands,
   `USING` and `WITH CHECK` expressions. A free-form PostgreSQL custom setting
   such as `app.jwt.account_id` is never an authority boundary: the runtime
   login can issue `SET`, `SET LOCAL` or `set_config` for an arbitrary two-part
   setting, so an RLS predicate must not trust that value by itself. Production
   uses either a tenant-bound serving identity whose protected catalog mapping
   derives the tenant from `session_user`, or a separately trusted database
   authorization broker. The mapping is one-to-one for both alternating logins,
   owned by a non-runtime role and inaccessible for effective DML, DDL,
   ownership or default-privilege mutation through any login, reachable role or
   `PUBLIC`. Catalog and live tamper-negative tests prove those properties.
   Rotation establishes and validates the new mapping before promotion, and
   retires the stale mapping only after the old login is unusable.
   In the broker design the application runtime has no database
   credential or network path; the broker receives a non-forgeable,
   audience-bound, short-lived and single-use authorization capability from an
   identity that the runtime cannot assume, validates issuer, subject, tenant,
   operation, expiry and replay state, and only then establishes the
   transaction-local tenant context. The runtime cannot mint, alter or select
   that context. Same-tenant positive operations succeed;
   cross-tenant `SELECT`, `INSERT`, `UPDATE` and `DELETE` all fail without
   changing rows. Live negative tests run as the actual application runtime and
   attempt direct database access, `SET LOCAL`, `set_config`, a victim tenant,
   an altered or replayed capability, another tenant's login and a broker
   bypass. In a tenant-bound connection PostgreSQL may accept the inert custom
   setting, but it cannot change the authorization result; in a broker design
   the application runtime cannot connect. Every victim-tenant operation fails.
   Connection reuse across two tenants proves no context leaks. Background
   aggregation is a distinct non-serving identity whose signed assignment or
   tenant-bound login permits only the enumerated tenant and time window; it
   cannot choose an arbitrary tenant, and no global or owner/BYPASSRLS query is
   permitted. For every runtime, broker, aggregation, inherited-role and
   `PUBLIC` path, catalog ACL checks and reached live commands prove denial of
   PostgreSQL 16 `TRUNCATE`, `REFERENCES` and `TRIGGER` privileges plus the
   ownership-dependent maintenance operations named in gate 5.

   Whole-table locking is a separate availability boundary from RLS and row
   locking. Under PostgreSQL 16, a login with `UPDATE`, `DELETE` or `TRUNCATE`
   can request every `LOCK TABLE` mode, including `ACCESS EXCLUSIVE`; FORCE RLS
   does not make that tenant-scoped. Release tests run as every actual login
   through every direct endpoint and RDS Proxy or other intermediary, request
   every lock mode over every shared table, partition and reachable view, and
   use ordinary same-tenant DML as the non-vacuous positive control. A shared
   direct-login design passes only if the operation is denied or a trusted
   layer outside the compromised session enforces an absolute transaction
   lifetime and terminates the backend and pinned intermediary connection.
   Session-controlled `statement_timeout`, `lock_timeout` and
   idle-in-transaction settings are not that control because an active
   malicious transaction can keep running. If direct-login DML inherently
   permits the global lock, the selected architecture uses broker-mediated SQL
   with the application denied database credentials and network reachability,
   or physically isolated tenant storage. Tests prove a pinned proxy connection
   cannot preserve a lock beyond the absolute gate and that a killed request
   cannot reacquire it outside a fresh authorized capability.

   Identifier generation and asynchronous notifications are also explicit
   tenant-boundary surfaces rather than incidental database features. The
   allowlist uses per-tenant or cryptographically opaque identifiers and grants
   no shared sequence access unless a separately approved design proves that
   returned values and visible state disclose no victim activity. Alternating
   victim and attacker sessions exercise `nextval`, `currval`, `lastval`,
   `setval`, every visible sequence catalog/view and transaction rollback,
   comparing returned values, visibility and durable state. The release
   inventory names every notification producer, consumer and channel derivation
   in source and the running system. Actual-login tests attempt victim-payload
   interception, channel guessing, event spoofing, long-listener queue
   retention and volume exhaustion; no tenant data, authorization decision,
   cross-tenant side effect or unbounded shared-queue consumption is observable.
   Because PostgreSQL does not object-ACL `LISTEN` and `NOTIFY`, a design whose
   direct credential can violate any of those boundaries must use the same
   trusted broker or physical tenant isolation rather than treating ACLs or
   FORCE RLS as sufficient.

   Catalog inspection also enumerates every reachable non-internal
   `pg_trigger` entry, including partition clones, with its owner, timing,
   events, `WHEN` expression, enabled mode, trigger function, security mode,
   fixed `search_path` and complete read/write dependency graph. Every table and
   domain `CHECK` constraint is enumerated with its transitive function,
   operator, cast and body dependencies. A source-version-pinned PostgreSQL 16
   catalog inventory applies the same closure to every `pg_node_tree` or stored
   SQL-expression field, including `pg_rewrite.ev_action`/`ev_qual`,
   `pg_trigger.tgqual`, `pg_constraint.conbin`, `pg_attrdef.adbin`,
   `pg_policy.polqual`/`polwithcheck`, `pg_index.indexprs`/`indpred`,
   `pg_partitioned_table.partexprs`, `pg_class.relpartbound`,
   `pg_proc.proargdefaults`/`prosqlbody`, `pg_type.typdefaultbin`,
   `pg_statistic_ext.stxexprs` and every `pg_publication_rel.prqual`. It
   therefore covers routine argument defaults, routine SQL bodies, column and
   domain defaults, stored generated columns, every unique or non-unique index
   expression/predicate, partition bounds/expressions, extended-statistics
   expressions and publication row filters. Each expression is absent or
   explicitly allowlisted only after transitive function/operator/cast/body
   closure and a reached probe under its actual caller, owner/maintenance,
   autovacuum or logical-replication execution identity.

   The same source-version-pinned closure applies to every catalog OID reference
   capable of implicit code execution, not only stored expression trees. For
   every reachable type it inventories and closes `pg_type` input, output,
   receive, send, typmod input/output, analyze and subscripting handlers, plus
   every applicable `pg_range` canonicalization, subtype-difference and
   multirange constructor function. For every reachable index, it follows
   `pg_index.indclass` and `indcollation` through `pg_opclass`, `pg_opfamily`,
   `pg_am`, `pg_amop` and `pg_amproc`, closing every selected access method,
   operator, operator implementation and support function. For every reachable
   foreign-key or exclusion constraint it also closes the complete
   `pg_constraint` equality and exclusion operator arrays, including
   `conpfeqop`, `conppeqop`, `conffeqop` and `conexclop`, through the same
   operator-family and implementation graph. Each reached hook records owner,
   security mode, language/native implementation or inspectable body, complete
   transitive dependencies and its actual caller, owner, maintenance,
   autovacuum or logical-replication execution identity. String-literal or
   dynamic SQL bodies, expression fields, publications or implicit hook graphs
   whose read/write and code dependencies cannot be closed are rejected rather
   than treated as absent from `pg_depend`.

   Catalog closure is not accepted as evidence about native modules. On every
   current Aurora instance, release evidence inventories the applied
   `shared_preload_libraries`, `session_preload_libraries` and
   `local_preload_libraries` settings plus every bounded-user-loadable
   `$libdir/plugins` module. The native inventory is the union of those
   preload/plugin modules and every library reachable through `pg_proc.probin`,
   procedural-language handlers, transforms and other on-demand native
   providers under the applied `dynamic_library_path`. Evidence resolves each
   actual library version or digest and closes its initialization, planner,
   executor, utility and other hooks, background workers, routine effects,
   execution identities and read/write/logging effects. Actual-login probes deny
   `LOAD` and a connection-start `local_preload_libraries` setting for every
   bounded role. An unavailable binary or source, unresolved effect, or active
   or loadable native hook graph that cannot be closed fails release.

   Actual-login probes exercise direct domain conversion and every applicable
   path through each rule, trigger, constraint, policy, default, generated
   column, index and partition expression. They separately reach text/CSV and
   binary `COPY FROM`/`COPY TO` so type input/output and receive/send hooks
   execute, plus applicable range, subscripting, index scan/write, `ANALYZE`,
   uniqueness, exclusion and foreign-key paths under each real execution
   identity. The statement matrix covers direct DML plus PostgreSQL 16 `MERGE`,
   conflict and no-conflict paths for both `INSERT ... ON CONFLICT DO NOTHING`
   and `DO UPDATE`. `ON CONFLICT DO UPDATE` probes include the conflicting
   row lock when its `WHERE` clause prevents the update. Lock-oracle fixtures use
   a privileged concurrent session that is proven to hold the victim lock, and
   cover `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE` and `FOR KEY SHARE` with
   plain bounded waits, `NOWAIT` and `SKIP LOCKED`; an unlocked positive control
   proves each path is reached. `MERGE` separately reaches matched `UPDATE`,
   `DELETE` and `DO NOTHING`, not-matched `INSERT` and `DO NOTHING`, plus
   statement-trigger effects for specified but untaken actions. Victim-existing,
   victim-absent and unlocked-control cases have indistinguishable returned
   results, SQLSTATE/error classification, bounded timing and row effects, and
   prove that no cross-tenant row, migration-ledger entry or other protected
   object changes. Absence of runtime `TRIGGER` privilege or routine `EXECUTE`
   privilege is not accepted as evidence about an existing trigger's execution.

   Constraint-oracle review catalogs every `pg_index.indisunique` entry and
   every primary-key, unique, foreign-key and exclusion constraint, including
   partial/expression unique indexes, partitioned parents and every child
   partition/index. Tenant-table identities and references include the
   tenant/account key. A privileged observer first proves the victim-existing
   and victim-absent fixtures are present as intended. Isolated primary-key and
   unique/index probes then succeed for the caller in both cases, proving
   tenant-qualified identity prevents a cross-tenant collision. Both isolated
   foreign-key probes fail with indistinguishable caller-visible status, error
   classification and row effects, while a same-tenant-parent positive control
   succeeds. Exclusion-constraint probes receive the same reached,
   positive-controlled treatment. Any exceptional design must prove an
   equivalent non-oracular boundary before release.

9. **Identity operations prove outcomes separately.** Connections assert
   `session_user = current_user = <active bounded login>`. `RESET ROLE` must
   return to that same authenticated login. `SET ROLE` to migrator/master and
   `SET SESSION AUTHORIZATION` to migrator/master are independently rejected;
   tests do not treat their authorization semantics as equivalent.
10. **Fail-closed ordering and recovery.** Migrator/bootstrap and rotation are
    idempotent and validate all IAM, Kubernetes and PostgreSQL postconditions.
    A failed Job or failed `AWSPENDING` probe cannot promote a secret stage or
    start/continue the runtime rollout. Retry, rollback and stale-stage
    retirement are exercised, including replica overlap, asynchronous instance
    recovery, failover or endpoint-membership change during the login-denial
    bracket, a retiring-role prepared transaction and a partial rollout.
11. **Value-free receipts.** Evidence ties workload/role ARNs, ServiceAccount
    names, secret ARNs and stages, database role names, migration digest and
    validation outcomes together without emitting any password, token or
    secret-derived digest.
